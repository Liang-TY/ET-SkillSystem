# 帧同步包代码分析（cn.etetet.lockstep）

基于 ET9 框架的预测回滚帧同步实现。

---

## 一、整体方案和思路

这个包实现的是一个经典的**预测回滚帧同步**（Predictive Rollback Lockstep）方案：

1. **固定帧率逻辑**：逻辑以 50ms 一帧（20fps）运行，所有逻辑计算使用定点数（TrueSync），不依赖浮点数，保证跨端确定性
2. **客户端预测**：客户端不等服务器返回，直接预测最多 5 帧往前跑
3. **服务器权威**：服务器收集所有玩家输入，组装成 `OneFrameInputs`（一帧内所有玩家的输入集合）广播给所有人
4. **回滚纠正**：客户端收到服务器权威帧后，与自己之前的预测对比；如果不一致就回滚到上一个正确的快照，用正确的输入重新模拟
5. **Hash 校验**：每帧对 LSWorld 做序列化后计算 hash，客户端上报 hash 给服务器，服务器对比，不一致就通知客户端，用于排查不同步问题

## 四、帧同步具体流程

### 阶段1：匹配 → 建房

```
客户端                 Gate                  Match               Map               Room(Fiber)
  │                     │                     │                   │                     │
  │──C2G_Match─────────>│                     │                   │                     │
  │                     │──G2Match_Match──────>│                   │                     │
  │                     │                     │ 等待凑够人数        │                     │
  │                     │                     │──Match2Map_GetRoom────────────────────>│
  │                     │                     │                   │ 创建新Room Fiber     │
  │                     │                     │                   │──RoomManager2Room_Init──────────>
  │                     │                     │<──Map2Match_GetRoom(ActorId)───────────│
  │<──Match2G_NotifyMatchSuccess──────────────│                   │                     │
```

1. 客户端发 `C2G_Match` → Gate 转发给 Match 组件
2. Match 组件等凑够 `MatchCount`（当前配置=1人，demo 用），向随机一个 Map 服务申请房间
3. Map 服务调用 `FiberManager.Instance.Create` 创建一个独立 **RoomRoot Fiber**（独立线程），每个房间一个 Fiber
4. 返回 Room 的 ActorId，Match 通知 Gate → 客户端

### 阶段2：进入战斗

5. 客户端收到匹配成功，执行 `LSSceneChangeHelper.SceneChangeTo()`：
   - 创建 `Room` 实体和 `LSWorld`
   - 发 `C2Room_ChangeSceneFinish` 通知服务器场景加载完毕
   - 等待服务器发 `Room2C_Start`

6. 服务端 `C2Room_ChangeSceneFinishHandler`：
   - 检查所有玩家都加载完毕（Progress=100）
   - 初始化 Room（`room.Init`）：设置起始时间、创建 LSUnit
   - 挂载 `LSServerUpdater`（服务端帧驱动）
   - 广播 `Room2C_Start` 给所有玩家

7. 客户端收到 `Room2C_Start` → `room.Init()` → 挂载 `LSClientUpdater`

### 阶段3：帧循环（核心）

**服务端** `LSServerUpdaterSystem.Update`：

```
每50ms一个逻辑帧：
  1. AuthorityFrame + 1
  2. 从 FrameBuffer 取该帧的 OneFrameInputs（客户端已经写入了自己的输入）
  3. 如果某个玩家输入没到，用上一帧的输入兜底
  4. 广播这一帧的 OneFrameInputs 给所有客户端
  5. 调用 room.Update(oneFrameInputs) → 驱动 LSWorld 逻辑
```

**客户端** `LSClientUpdaterSystem.Update`：

```
每帧检查时间：
  1. 如果当前时间 < 下一帧的时间，不推进（等时间到）
  2. 如果 PredictionFrame - AuthorityFrame > 5，不推进（预测太远了）
  3. PredictionFrame++
  4. 获取该帧的输入：
     - 如果 <= AuthorityFrame：用权威数据
     - 如果 > AuthorityFrame（预测）：复制上一帧别人的输入，用自己的新输入
  5. 调用 room.Update(oneFrameInputs) → 驱动 LSWorld
  6. 发送 FrameMessage（自己的输入+帧号）给服务器
```

**LSInputComponentSystem.LSUpdate** — 每个单位每帧执行的逻辑：

```csharp
// 读取输入，移动单位（定点数运算，确定性）
TSVector2 v2 = self.LSInput.V * 6 * 50 / 1000;
unit.Position += new TSVector(v2.x, 0, v2.y);
unit.Forward = unit.Position - oldPos;
```

### 阶段4：回滚纠正

客户端收到服务器 `OneFrameInputs` 时（`OneFrameInputsHandler`）：

```
1. AuthorityFrame++
2. 对比服务器发来的权威输入 vs 本地预测输入
3. 如果一致 → 直接确认，记录录像，上报hash
4. 如果不一致 → 执行回滚（LSClientHelper.Rollback）：
   a. 销毁当前 LSWorld
   b. 从 FrameBuffer 中反序列化该帧的快照，恢复 LSWorld
   c. 用权威输入重新执行那一帧 (room.Update)
   d. 从 AuthorityFrame+1 到 PredictionFrame，逐帧重新模拟（重新预测）
```

### 阶段5：Hash 校验

- 客户端每帧确认后，对 LSWorld 做序列化算 hash，发 `C2Room_CheckHash` 给服务器
- 服务器对比 hash（`C2Room_CheckHashHandler`），不一致则发 `Room2C_CheckHashFail` 把服务端的 LSWorld 序列化发回客户端，用于调试

## 五、关键设计细节

- **FrameBuffer**：环形缓冲区，用 `% capacity` 取模索引，预分配内存，存每帧的输入、快照（MemoryBuffer）、hash
- **快照**：每帧都保存 LSWorld 序列化快照到 FrameBuffer，用于回滚时恢复；录像则每 60 秒（`SaveLSWorldFrameCount`）存一个完整快照
- **时间膨胀**：服务器会周期性检测客户端的时间偏差，发 `Room2C_AdjustUpdateTime` 让客户端动态调整 `FixedTimeCounter.Interval`（40ms~66ms 范围），实现追帧/减速
- **断线重连**：`LSSceneChangeHelper.SceneChangeToReconnect()` 支持从指定帧恢复
- **每房间独立 Fiber**：利用 ET9 的 Fiber 机制，每个房间一个独立线程，互不影响

### 第1步：键盘输入采集（Unity Update，每帧）


### 第3步：逻辑帧更新 — 移动 LSUnit

`RoomSystem.Update`：

```csharp

foreach (var kv in oneFrameInputs.Inputs)
{
    LSUnit lsUnit = unitComponent.GetChild<LSUnit>(kv.Key);

```

`LSInputComponentSystem.LSUpdate`（定点数移动）：

```csharp

unit.Position += new TSVector(v2.x, 0, v2.y);
unit.Forward = unit.Position - oldPos;
```

### 第4步：表现层同步 — 移动 GameObject + 播动画

`LSUnitViewSystem.Update`：

```csharp
LSUnit unit = self.GetUnit();
Vector3 unitPos = unit.Position.ToVector();

if (unitPos != self.Position)
{
    self.totalTime = distance / speed2;     // 计算插值时间
    self.Position = unit.Position.ToVector(); // 记录目标位置
}

// 根据输入判断动画
LSInput input = unit.GetComponent<LSInputComponent>().LSInput;
if (input.V != TSVector2.zero)
    self.GetComponent<LSAnimatorComponent>().SetFloatValue("Speed", speed2);  // 跑步
else
    self.GetComponent<LSAnimatorComponent>().SetFloatValue("Speed", 0);       // 站立

// 平滑插值移动 GameObject
self.Transform.position = Vector3.Lerp(self.Transform.position, self.Position, self.t / self.totalTime);
self.Transform.rotation = Quaternion.Lerp(self.Transform.rotation, self.Rotation, self.t / 1f);
```

```
         ▼

         ▼
```

## 七、Room 是由独立服务管理的吗

**Room 不是由一个独立的"Room 服务进程"管理的，而是由 Map 服务进程内创建的独立 Fiber 管理的。**

创建房间时（`Match2Map_GetRoomHandler.cs`）：

```csharp
Fiber fiber = root.Fiber(); // root 是 Map 场景
int fiberId = await FiberManager.Instance.Create(
    SchedulerType.ThreadPool, fiber.Zone, SceneType.RoomRoot, "RoomRoot");
```

这里是在 **Map 场景的 Handler** 里执行的，调用 `FiberManager.Instance.Create` 创建了一个 **RoomRoot Fiber**，而不是启动一个新进程。

### 架构对比

```
传统做法（进程级服务）：
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Gate进程  │  │ Match进程 │  │ Room进程  │  ← 每个是一个OS进程
└──────────┘  └──────────┘  └──────────┘

ET9的做法（Fiber级隔离，同进程内）：
┌─────────────────────────────────────────┐
│            同一个OS进程                   │
│  ┌────────┐ ┌────────┐ ┌────────────┐  │
│  │Map Fiber│ │Map Fiber│ │RoomRoot Fiber│ │  ← 每个是独立Fiber（线程池调度）
│  │ (匹配) │ │ (匹配) │ │  (房间逻辑)  │  │
│  └────────┘ └────────┘ └────────────┘  │
│         Actor消息机制互相通信              │
└─────────────────────────────────────────┘
```

### 和登录中心的区别

| | 登录中心（如 Gate/Login 服务） | 房间（RoomRoot Fiber） |
|---|---|---|
| 隔离级别 | 独立 OS 进程 | 同进程内的独立 Fiber |
| 生命周期 | 进程启动就存在，长期运行 | 按需创建，战斗结束即销毁 |
| 数量 | 少量固定实例 | 每场战斗一个，动态伸缩 |
| 通信 | 跨进程网络消息 | 进程内 Actor 消息（不走网络） |
| 线程 | 可以独占一个线程 | 线程池调度 |

本质上，ET9 的 Fiber 类似 **Erlang 的轻量级进程**概念——逻辑上完全隔离、消息驱动，但物理上共用一个 OS 进程。

## 八、Match 和 Map 是独立服务吗

**不一定是，取决于部署配置。** 这是 ET 架构的核心设计理念：代码不关心部署方式。

服务端启动入口 `EntryEvent2_InitServer.cs`：

```csharp
var scenes = StartSceneConfigCategory.Instance.GetByProcess(process);
foreach (StartSceneConfig startConfig in scenes)
{
    await FiberManager.Instance.Create(
        SchedulerType.ThreadPool, startConfig.Id, startConfig.Zone,
        sceneType, startConfig.Name);
}
```

从 Excel 配置表里读取当前进程应该启动哪些场景。

|----|-----------|------|---------|

## 九、传统帧同步中怪物的同步方式

核心原则：**怪物没有任何数据通过网络同步，所有客户端各自本地算出完全一样的结果。**

```
玩家A的客户端                服务器                玩家B的客户端
┌──────────────┐        ┌──────────┐        ┌──────────────┐
│ 玩家A输入: 向前走│───────>│ 收集所有人输入 │<───────│ 玩家B输入: 攻击  │
│ 玩家A输入: 攻击  │       │ 转发给所有人  │        │ 玩家B输入: 向前走│
└──────┬───────┘        └──────────┘        └──────┬───────┘
       │ 广播 {A:走+攻, B:攻+走}                    │
       ▼                                          ▼
┌──────────────────┐                    ┌──────────────────┐
│ 本地执行同一份逻辑  │                    │ 本地执行同一份逻辑  │
│ 1.移动玩家A         │                    │ 1.移动玩家A         │
│ 2.移动玩家B         │                    │ 2.移动玩家B         │
│ 3.怪物AI决策        │  ← 同一份代码       │ 3.怪物AI决策        │
│ 4.怪物移动          │  ← 同样的输入       │ 4.怪物移动          │
│ 5.伤害计算          │  ← 同样的结果       │ 5.伤害计算          │
│ 6.怪物扣血          │                    │ 6.怪物扣血          │
└──────────────────┘                    └──────────────────┘
```

**网络上只传输玩家的输入**（按键、摇杆方向、技能按钮），怪物的一切行为全部由本地确定性模拟产生。

### 怪物位置 — 确定性AI驱动

```
每帧逻辑更新：
  怪物AI读取：
    - 怪物当前状态（巡逻/追击/攻击）
    - 所有玩家的位置（本地已有）
    - 仇恨列表（确定性计算的）

  AI决策（纯函数，确定性）：
    if (距离最近的玩家 < 5米) → 追击该玩家
    if (距离最近的玩家 < 1.5米) → 停下来准备攻击
    else → 继续巡逻路线

  移动计算（定点数）：
    怪物.Position += 方向 * 速度 * deltaTime
```

### 怪物血量 — 确定性伤害计算

```
帧 N：玩家B按下攻击键
  → 输入: {PlayerB: Button=攻击}

所有客户端各自本地执行：
  1. 检查：玩家B是否在攻击范围内？ → 是（所有人算出一样的距离）
  2. 检查：攻击CD是否好了？ → 是（所有人从同一帧开始计时）
  3. 计算伤害：
     damage = 攻击力 * 技能倍率 - 防御力 * 减伤系数
     （纯数学，定点数，确定性）
  4. 怪物.HP -= damage

  → 所有客户端的怪物HP剩余完全一致
```

### 怪物放技能 — 确定性条件触发

```
怪物AI每帧判断：
  if (怪物.HP < 30% && 技能CD_ready && 随机数种子 == 某值)
  {
      怪物.释放技能("狂暴斩");
      技能CD = 10秒;
  }
```

关键：随机数必须用 seeded PRNG（种子在战斗开始时确定），不能用系统随机数。

### 帧同步的要求

| 要求 | 说明 |
|------|------|
| **确定性浮点** | 不能用 `float`/`double`（不同CPU结果不同），必须用定点数（如 TrueSync） |
| **确定性随机** | 用固定种子的伪随机数生成器 |
| **逻辑完全相同** | 不能有 `if (isLocalPlayer)` 这种分支影响逻辑 |
| **不依赖帧率** | 逻辑用固定时间步长（如50ms），不能用 `Time.deltaTime` |
| **不依赖外部状态** | 不能查数据库、读文件、调系统API |

### 和状态同步的对比

| | 帧同步 | 状态同步（如魔兽世界） |
|---|---|---|
| 怪物HP在哪算 | 每个客户端各自算 | 服务器算，广播结果给客户端 |
| 网络传输 | 只传玩家输入（几字节/帧） | 传输所有实体状态（位置、血量、buff等） |
| 带宽消耗 | 极低 | 较高 |
| 作弊风险 | 客户端知道全部数据，容易做透视 | 客户端只知道服务器告诉它的 |
| 断线重连 | 需要从头回放所有帧（或快进快照） | 直接拉取当前状态即可 |

## 十、玩家卡住会阻塞别人吗

**不会。** 服务器不等任何人。

服务端帧推进逻辑（`LSServerUpdaterSystem.cs`）：

```csharp
// 有人输入的消息没过来，给他使用上一帧的操作
foreach (long playerId in room.PlayerIds)
{
    if (oneFrameInputs.Inputs.ContainsKey(playerId))
        continue;

    if (preFrameInputs != null && preFrameInputs.Inputs.TryGetValue(playerId, out LSInput input))
        oneFrameInputs.Inputs[playerId] = input;  // 兜底：用上一帧的输入
    else
        oneFrameInputs.Inputs[playerId] = new LSInput();  // 兜底：空输入
}
```

### 实际发生的时间线

```
服务端                玩家B(正常)            玩家A(卡住)
  │                     │                     │
  │ 帧N: 广播           │← 收到，怪物还剩1刀     │← 收到，怪物还剩1刀
  │                     │                     │
  │ 帧N+1:              │                     │
  │ B发了攻击输入         │                     │ ×××网络卡住，输入没发出去
  │ A没输入→用上一帧      │                     │
  │ 广播 {A:走, B:攻}    │← 收到               │ ✗ 没收到
  │ 本地执行: 怪物死亡!    │ 本地执行: 怪物死亡!    │
  │                     │                     │
  │ 帧N+2: 正常推进      │ 继续游戏              │ ✗ 还没收帧N+1
  │                     │                     │
  │  ... 2秒后网络恢复     │                     │
  │                     │                     │← 收到一堆积压的帧
  │                     │                     │ 本地快进执行
  │                     │                     │ 但A在帧N+1没有攻击输入
  │                     │                     │ 所以A的客户端：怪物没死！
```

- **玩家B不会卡住**，他正常收到了所有帧
- **玩家A不会卡住别人**，服务器用兜底输入替他推进了
- **A 恢复后和 B 的状态不一致了**：B 那边怪物死了，A 那边怪物没死
- 这时需要 Hash 校验机制检测不同步

### 处理方式

| 方式 | 做法 |
|------|------|
| **断线重连** | A 卡太久直接判定掉线，重连后从快照恢复到最新状态 |
| **等待机制** | 重要时刻（如 Boss 死亡判定）可以设一个短暂的输入等待窗口 |
| **快进追赶** | A 恢复后快速模拟积压的帧追上大家（`LSClientUpdater` 的 while 循环支持一帧内跑多步） |
| **强制同步** | 检测到 hash 不一致时，服务器下发完整快照，客户端用服务端状态覆盖本地状态 |

## 十一、帧同步中的通关判定

**"玩家B的怪物死了，A的怪物没死" 这种情况在正确运行的帧同步中不会发生。**

帧同步的保证是：**同代码 + 同输入 = 同结果**。怪物死亡是一个确定性判定：

```
帧N+1，所有客户端各自执行：
  怪物.HP -= 伤害           // 同样的HP，同样的伤害 → 同样的结果
  if (怪物.HP <= 0)
      怪物.死亡()
  if (所有怪物.都死了)
      通关()
```

每个客户端跑的是**同一份代码、同一份输入**，怪物在同一帧扣同样的血，在同一帧死亡。通关判定在所有客户端上**一定在同一帧触发**。

### 如果真的出现不同步

如果出现"A的怪物没死B的怪物死了"，说明帧同步已经坏了（不同步 bug），不只是通关判定的差异，怪物的位置、技能、所有状态都不一样了。这时候应该做的是修复不同步，而不是设计"以谁为准"的通关判定。

### 保险机制

实际项目中可以在通关这种关键时刻加一层保险：

```
客户端本地判定通关后：
  1. 向服务器发一条"我判定通关了"的消息
  2. 服务器收集所有人的判定
  3. 全部一致 → 确认通关，进入结算
  4. 有人不一致 → 说明不同步了，用服务端快照纠正
```

核心认知：帧同步中 **不存在"我的怪物"和"你的怪物"**，只有一个世界，所有人看到的是同一份模拟。

## 十二、技能回滚的实现方案

### 核心思路

**逻辑层自动回滚，表现层手动同步。**

`LSClientHelper.Rollback` 做的事：

```csharp
// 1. 销毁当前 LSWorld
room.LSWorld.Dispose();

// 2. 从快照恢复 LSWorld（包含所有逻辑状态）
room.LSWorld = room.GetLSWorld(SceneType.LockStepClient, frame);

// 3. 重新执行后续帧
for (int i = room.AuthorityFrame + 1; i <= room.PredictionFrame; ++i)
    room.Update(oneFrameInputs);

// 4. 通知表现层同步
RunLSRollbackSystem(room);
```

逻辑层的状态（包括技能状态）在步骤 2 已经自动恢复了。问题是表现层（特效、动画）需要额外处理。

### 逻辑层：技能状态设计

```csharp
// Model/Share/LSSkillComponent.cs
[ComponentOf(typeof(LSUnit))]
[MemoryPackable]
public partial class LSSkillComponent: LSEntity, IAwake, ISerializeToEntity
{
    [MemoryPackOrder(0)]
    public int CurrentSkillId;      // 当前释放的技能ID，0表示无

    [MemoryPackOrder(1)]
    public int SkillStage;          // 技能阶段（1段/2段/3段）

    [MemoryPackOrder(2)]
    public int StageFrame;          // 进入当前阶段的帧号

    [MemoryPackOrder(3)]
    public Dictionary<int, int> Cooldowns = new();  // skillId -> 剩余帧数
}
```

技能逻辑在 `LSUpdate` 中执行：

```csharp
[LSEntitySystem]
private static void LSUpdate(this LSSkillComponent self)
{
    // 更新冷却
    var keys = self.Cooldowns.Keys.ToList();
    foreach (var skillId in keys)
    {
        if (--self.Cooldowns[skillId] <= 0)
            self.Cooldowns.Remove(skillId);
    }

    // 检查当前技能阶段是否该结束了
    if (self.CurrentSkillId != 0)
    {
        var config = SkillConfigCategory.Instance.Get(self.CurrentSkillId);
        int stageDuration = config.StageFrames[self.SkillStage - 1];

        int currentFrame = self.LSWorld().Frame;
        if (currentFrame - self.StageFrame >= stageDuration)
        {
            if (self.SkillStage < config.StageCount)
            {
                self.SkillStage++;
                self.StageFrame = currentFrame;
            }
            else
            {
                self.CurrentSkillId = 0;
                self.SkillStage = 0;
            }
        }
    }
}

// 释放技能
public static bool TryCastSkill(this LSSkillComponent self, int skillId)
{
    if (self.Cooldowns.ContainsKey(skillId))
        return false;
    if (self.CurrentSkillId != 0)
        return false;

    self.CurrentSkillId = skillId;
    self.SkillStage = 1;
    self.StageFrame = self.LSWorld().Frame;
    self.Cooldowns[skillId] = SkillConfigCategory.Instance.Get(skillId).CooldownFrames;
    return true;
}
```

关键：`LSSkillComponent` 是 `MemoryPackable`，会被序列化到快照里，回滚时自动恢复。

### 表现层：技能视图回滚

```csharp
// ModelView/Client/LSSkillViewComponent.cs
[ComponentOf(typeof(LSUnitView))]
public class LSSkillViewComponent: Entity, IAwake, IDestroy, ILSRollback
{
    public Dictionary<string, ParticleSystem> ActiveEffects = new();
    public int LastSkillId;
    public int LastStage;
}
```

```csharp
// HotfixView/Client/LSSkillViewSystem.cs
[EntitySystemOf(typeof(LSSkillViewComponent))]
public static partial class LSSkillViewSystem
{
    [EntitySystem]
    private static void Update(this LSSkillViewComponent self)
    {
        LSUnit unit = self.GetParent<LSUnitView>().GetUnit();
        LSSkillComponent skillComp = unit.GetComponent<LSSkillComponent>();

        if (skillComp.CurrentSkillId != self.LastSkillId ||
            skillComp.SkillStage != self.LastStage)
        {
            self.OnSkillStateChange(skillComp.CurrentSkillId, skillComp.SkillStage);
            self.LastSkillId = skillComp.CurrentSkillId;
            self.LastStage = skillComp.SkillStage;
        }
    }

    // ★ 关键：回滚时调用
    [EntitySystem]
    private static void LSRollback(this LSSkillViewComponent self)
    {
        // 1. 清理所有当前特效
        self.ClearAllEffects();

        // 2. 从逻辑层读取正确的技能状态
        LSUnit unit = self.GetParent<LSUnitView>().GetUnit();
        LSSkillComponent skillComp = unit.GetComponent<LSSkillComponent>();

        // 3. 更新记录的状态
        self.LastSkillId = skillComp.CurrentSkillId;
        self.LastStage = skillComp.SkillStage;

        // 4. 根据正确状态重新播放特效
        if (skillComp.CurrentSkillId != 0)
        {
            string effectPath = $"Effects/Skill_{skillComp.CurrentSkillId}_Stage{skillComp.SkillStage}";
            self.PlayEffect(effectPath, $"Skill_{skillComp.CurrentSkillId}_{skillComp.SkillStage}");
        }
    }
}
```

### 场景1：本地释放技能，服务端说你没释放

```
帧100（预测）：
  本地: 玩家按下技能键 → TryCastSkill(101)
        LSSkillComponent.CurrentSkillId = 101, Stage = 1
        表现层: 播放火球特效

帧100（服务端权威返回）：
  服务端: 你的输入没送到（网络延迟），用上一帧空输入
        LSSkillComponent.CurrentSkillId = 0（没有技能）

  客户端收到 OneFrameInputs:
    对比发现不一致 → 触发 Rollback
    → 恢复 LSWorld 快照（没有技能状态）
    → 调用 LSRollbackSystem
    → LSSkillViewComponent.LSRollback():
       - 清除火球特效
       - 读取 CurrentSkillId = 0
       - 不播放任何特效
```

### 场景2：二段技能回滚到一段

```
帧100: 释放技能101一段
  CurrentSkillId = 101, Stage = 1
  播放一段特效（蓄力）

帧105（预测）: 进入二段
  CurrentSkillId = 101, Stage = 2
  播放二段特效（释放）

帧105（服务端）: 一段持续时间应该是10帧，你才过了5帧
  CurrentSkillId = 101, Stage = 1  ← 服务端还是一段

  客户端收到后对比不一致 → Rollback
  → 恢复 LSWorld（Stage = 1）
  → LSSkillViewComponent.LSRollback():
     - 清除二段特效（释放动画）
     - 读取 Stage = 1
     - 重新播放一段特效（蓄力继续）
```

### 总结

| 层次 | 回滚机制 | 开发者要做的 |
|------|----------|-------------|
| **逻辑层** | 自动恢复 | 把技能状态设计成 `MemoryPackable` 组件，存在 LSWorld 里 |
| **表现层** | 手动同步 | 实现 `ILSRollback` 接口，在 `LSRollback` 里清理特效 + 按新状态重建 |

**本质**：逻辑层的回滚是框架帮你做的（恢复快照），表现层的回滚是开发者自己做的（响应 `LSRollback` 回调，把视觉同步到逻辑）。特效不需要"回退播放"，直接销毁重来。
