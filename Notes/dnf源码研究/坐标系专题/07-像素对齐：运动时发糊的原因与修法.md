# 07 · 像素对齐：为什么"静止清晰、一动就糊"

> **现象**：Unity 里加载 img 帧渲染角色，静止时画面清晰；按键移动后精灵看起来发糊/不清晰。
> **结论先行**：是的，本质就是**像素对齐（亚像素采样）**问题——运动时精灵落在"像素格子中间"，静态时（碰巧）落在格子点上。我们工程的叠加成因有三个，按嫌疑排序：
> ① 视图移动用 `Vector3.Lerp`，运动中坐标几乎每帧都是小数（主因）；
> ② 帧内容中心 `X + W/2` 在奇数宽高时产生 **0.5px 半像素相位**，动画换帧时翻转（次因）；
> ③ 相机"1 世界单位 = 多少屏幕像素"若不是整数，静止也在重采样（检查项，见 §4）。
> 本文所有行号引用当前工程代码。

---

## 1. 机理：亚像素采样在 Point / Bilinear 下的两种长相

DNF 资源是 1:1 像素图（1 DNF px = 1/100 Unity 单位 = 我们想要的 1 屏幕像素）。渲染时 GPU 按**精灵的世界坐标**对纹理采样：

- 精灵边缘正好压在屏幕像素格点上 → 1 纹理像素 = 1 屏幕像素 → **清晰**（静止时的你）；
- 精灵压在两个像素中间（坐标出现小数）→ 采样点落在像素边界：
  - **Point 采样**（我们的图集就是：`LSAnimResComponentSystem.cs:77 filterMode = FilterMode.Point`）：每个屏幕像素"抢"左边或右边的纹理像素，边缘一帧偏一帧偏右 → **像素沸腾/边缘爬动（shimmer/boil）**，观感就是"动起来不清晰"；
  - Bilinear 采样：相邻像素混色 → 经典**运动模糊**感。

我们的图集是 Point，所以严格说不是"糊"而是"抖/沸"——但眼睛的第一反馈都是"不清晰"。

**判别法**：运动中截图放大看边缘——边缘在"抖动跳变"= Point 亚像素；边缘"变灰变软"= 哪里有层 Bilinear。

## 2. 我们工程的三个成因（对号入座）

### ① 主因：移动平滑 = 小数坐标（`LSUnitViewSystem.cs:44-74`）

```csharp
const float speed = 6f;
if (screenPos != self.Position) { ... totalTime = distance / speed; ... }
self.t += Time.deltaTime;
self.Transform.position = Vector3.Lerp(self.Transform.position, self.Position, lerpT);
```

静止时 position 收敛到一个固定值（哪怕带小数，相位恒定 → 稳定，Point 下甚至显得很锐）；**一旦移动，Lerp 每帧产出新的小数坐标** → 亚像素相位逐帧变化 → 沸腾。

（相机当前不跟随角色——`LSCameraComponentSystem.cs:43` 的跟随被注释——所以只有这一处插值源，排除"相机+角色双重插值"。）

### ② 次因：奇数帧尺寸的 0.5px 相位翻转（`LSAnimResComponentSystem.cs:107`）

```csharp
centers[r.Id] = new Vector2(s.X + s.Width / 2f, s.Y + s.Height / 2f);   // 奇数 W/H → x.5 像素
```

move 动画各帧位图 54×101、57×103、59×94…… 奇偶交错：奇数帧内容中心带 **.5px**，偶数帧不带 → 摆位后 renderer 的 localPosition 每换一帧在"格点上/半格上"翻转 → 纵向（和横向）半像素抖动。走路时贴图本来就小幅度起伏，叠加这个就是"颗粒感/发虚"。

数学上脚底仍是稳的（底边 = 中心 − H/2，DNF 数据保证 ≈0），**不稳的是采样相位**——所以这不是坐标算错，是坐标没对齐像素格。

### ③ 检查项：相机像素比

"1 世界单位 = 多少屏幕像素"由相机 orthoSize 决定：`pxPerUnit = 屏幕高 / (2 × orthoSize)`。**必须等于 100（或至少是整数）**：

- 1080p、orthoSize = 5.4 → 1080/10.8 = **100** ✓
- 1080p、orthoSize = 5.0 → 108/单位 → 100px 的图被画进 108px → 重采样，像素宽度 1~2px 不均，静止也隐约有竖纹，运动放大

（场景相机的 orthoSize 我在本机代码里查不到配置值——**回 Unity 机确认这一项**：选中 Camera 看 Orthographic Size，1080p 设计分辨率下应为 5.4。）

## 3. 修法（按顺序做，通常第 1 步就好）

### 修法 A（主修）：渲染末段把位置吸附到像素格——snap

在**视图层**（逻辑层绝不能动，帧同步确定性！）对最终位置取整到 1/100 单位。放 `LSUnitViewSystem.Update` 的 Lerp 之后（或独立 LateUpdate 系统）：

```csharp
// Lerp 之后：
Vector3 p = self.Transform.position;
self.Transform.position = new Vector3(
    Mathf.Round(p.x * 100f) / 100f,
    Mathf.Round(p.y * 100f) / 100f,
    p.z);
```

- snap 后移动从"连续滑动"变成"逐像素步进"——**这是 2D 像素游戏的标准观感**（DNF 原版就是逐像素移动的）；
- 若步进感显得卡，先别加大平滑——去查 ③（像素比不是 100 时，snap 步长和屏幕像素不匹配，才是卡的根源）；
- snap 吸收了成因②（0.5px 被 round 到稳定格点），center 公式不用改；
- 弹/特效视图如出现同样问题，同法 snap（它们位置变化更剧烈，受益更明显）。

### 修法 B：相机像素比对齐（§4 检查项不通过才做）

- 固定设计分辨率 1080p → orthoSize = 5.4；
- 要多分辨率适配 → 用 Unity 的 **Pixel Perfect Camera** 组件（资产里带，正交相机直接加），或运行时按 `orthoSize = Screen.height / 2f / 100f` 自算（注意窗口拉伸时重算）。

### 修法 C：杂项检查（前两步无效再查）

| 检查 | 位置 | 期望 |
|---|---|---|
| 图集 filterMode | LSAnimResComponentSystem:77 | Point ✓（已对） |
| mipmap | :76 构造参数 false | ✓（已关） |
| AdditiveMaterial（LINEARDODGE 发光） | :36-39 | 确认它采样的也是同一张 Point 图集纹理 |
| MSAA / 后处理（bloom 等） | URP 资产/相机 | 像素风建议关 MSAA、不上 bloom |
| Sprite 缩放 | 任何 localScale ≠ 1 的层 | 有则重采样（非整数缩放=持续模糊） |

## 4. 回 Unity 机的验证步骤

1. 打印一次运动中的 `Transform.position`——看到满屏 3 位小数即实锤 ①；
2. 确认 Camera.orthographicSize（1080p 应 5.4）——③；
3. 加 snap（修法 A）→ 静止/运动对比截图放大看边缘；
4. 仍有 boil → 按 §3 C 表逐项查。

## 5. 与坐标系专题的关系（为什么记在这里）

这是 **÷100（PPU=100）管线的最后一环**：从 DNF 像素 → Unity 单位 → 屏幕像素，前面 01-05 篇管"算得对不对"，本篇管"落得齐不齐"。坐标算对了但没对齐像素格，观感照样错——这也是调试坐标问题时容易误判成"坐标 bug"的一类假象（06 篇 §0 的地图里可加一条：贴图"发糊/抖"先查像素对齐，别动坐标公式）。

## 6. 速查卡

1. 静止清晰、运动糊/抖 = 亚像素采样；Point 下是"沸腾"，Bilinear 下才是"真糊"。
2. 我们三个成因：Lerp 小数坐标（:44-74 主因）＋奇数帧 0.5px 相位（:107）＋相机像素比（待查）。
3. 主修 = 视图层 snap 到 1/100；**逻辑层（帧同步）绝对不动**。
4. 相机像素比必须整（1080p→orthoSize 5.4 = 100px/单位）。
5. snap 后逐像素步进是像素游戏正确观感，不是 bug。
