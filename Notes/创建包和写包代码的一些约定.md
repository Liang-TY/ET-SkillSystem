## 1. 包的目录结构

一个 ET 包通常包含以下目录：

```
cn.etetet.xxx/
├── Runtime/          # 程序集定义（asmdef）+ 纯工具类代码
├── Scripts/          # 业务代码（按 Model/Hotfix/ModelView/HotfixView 分层）
├── DotNet~/          # 服务端独立编译的 csproj 配置
├── Editor/           # Unity Editor 工具代码
├── package.json      # UPM 包依赖
└── link.xml          # HybridCLR 链接保留配置
```

## 2. 代码放在哪个目录

### 纯工具类（无 Unity 依赖、无 Entity/Component）→ Runtime/

像 `npkparser` 这种，不按 Model/Hotfix 分层，代码直接放 Runtime/：

```
cn.etetet.npkparser/
  Runtime/
    npkParser.asmdef          # 定义程序集
    NpkImgParser.cs           # 代码直接放这里
    AnimClipData.cs
```

### 业务代码（有 Entity/Component/System）→ Scripts/

按 Model/Hotfix/ModelView/HotfixView 分层，通过 `.asmref` 关联到对应程序集：

```
cn.etetet.lockstep/
  Scripts/
    Model/
      Client/LSUnit.cs                           # 数据定义
    Hotfix/
      Client/LSClientUpdaterSystem.cs            # 逻辑实现
    ModelView/
      Client/UI/UILSRoom/UILSRoom.cs             # 视图数据（需要 UnityEngine）
    HotfixView/
      Client/LSAnimResComponentSystem.cs         # 视图逻辑
      Client/AssemblyReference.asmref            # → { "reference": "ET.HotfixView" }
```

### 服务端代码 → Scripts/xxx/Server/ 或 Scripts/xxx/Share/

- `Server/` — 只在服务端运行
- `Share/` — 客户端和服务端都用
- `Client/` — 只在客户端运行

DotNet~/ 下的 csproj 通过通配符自动包含：

```xml
<Compile Include="$(SolutionDir)Packages\cn.etetet.*\Scripts\Model\Share\**\*.cs" />
<Compile Include="$(SolutionDir)Packages\cn.etetet.*\Scripts\Model\Server\**\*.cs" />
```

> **简单记：纯工具放 Runtime，业务代码按分层放 Scripts，DotNet~/ 里只放 csproj 配置不放代码。**

## 3. 四层分级的职责

| 目录 | 程序集 | 职责 | 引用 Unity? | 热更新 |
|------|--------|------|-------------|--------|
| Model/ | ET.Model | 数据定义：Entity、Component、接口 | 否 | 否（AOT） |
| Hotfix/ | ET.Hotfix | 逻辑实现：System、Handler | 否 | 是 |
| ModelView/ | ET.ModelView | 视图数据：需要 UnityEngine 的定义 | 是 | 否（AOT） |
| HotfixView/ | ET.HotfixView | 视图逻辑：渲染、UI、输入 | 是 | 是 |

为什么要 4 层：

- **服务端不能引用 UnityEngine** → Model/Hotfix 不引用 Unity
- **部分代码需要热更新** → Hotfix/HotfixView 独立 DLL，HybridCLR 可替换
- **数据层不能依赖逻辑层** → Model 和 Hotfix 是不同程序集，引用方向由 asmdef 控制

## 4. package.json 依赖 vs asmdef 引用

两者作用在不同层面，缺一不可：

### package.json — 包级别（UPM）

告诉 UPM "我这个包需要先安装哪些包"：

```json
"dependencies": {
    "cn.etetet.npkparser": "1.0.0",
    "cn.etetet.truesync": "3.0.0"
}
```

效果：UPM 把这些包解析进来。**仅此而已，不涉及编译。**

### asmdef references — 编译级别

告诉编译器 "我这个程序集能引用哪些其他程序集"：

```json
"references": ["ET.NpkParser", "ET.TrueSync"]
```

效果：这个 asmdef 下的代码才能 using 那些程序集里的类型。

### 关系

- **package.json 提供可能性**：包装了，里面的 asmdef 才可以被引用
- **asmdef 决定实际可见性**：包装了但不引用，代码里照样用不了

## 5. asmdef vs asmref vs csproj vs sln

### asmdef（Assembly Definition）

定义一个新程序集，声明名字和依赖：

```json
{ "name": "ET.HotfixView", "references": ["ET.NpkParser", "ET.Model"] }
```

放在 `Runtime/` 目录下。一个包可以有多个 asmdef（如 lockstep 有 5 个），也可以只有一个（如 npkparser）。

### asmref（Assembly Reference）

把当前目录的代码关联到已存在的程序集：

```json
{ "reference": "ET.HotfixView" }
```

放在 `Scripts/` 目录下。**注意：Scripts/ 里没有 asmdef，只有 asmref。**

### 对应关系

```
一个 asmdef → 一个程序集 → Unity 自动生成一个 csproj
```

```
ET.HotfixView.asmdef  →  ET.HotfixView 程序集  →  ET.HotfixView.csproj
ET.NpkParser.asmdef   →  ET.NpkParser 程序集   →  ET.Npk.csproj
```

### sln 怎么识别包

Unity.sln **不关心"包"的概念**，只认 csproj。Unity 扫描所有 asmdef，每个生成一个 csproj，全部塞进 sln：

```
Project("...") = "ET.HotfixView", "ET.HotfixView.csproj"
Project("...") = "ET.Model",      "ET.Model.csproj"
Project("...") = "ET.Npk",        "ET.Npk.csproj"         ← 来自 npkparser 包
Project("...") = "ET.Hotfix",     "ET.Hotfix.csproj"       ← 来自 lockstep 包
```

Rider 看到的是程序集列表，不是包。包只是文件系统上的组织方式。

> **总结：包是给 UPM 管依赖用的，asmdef 是给编译器划程序集用的，asmref 是把代码挂到程序集上用的，csproj/sln 是给 IDE 用的。四层各管各的。**

## 6. 为什么 lockstep 包定义 4 层 asmdef

lockstep 是**主业务包**，它定义的 4 个 asmdef 不是只给自己用的，而是给**所有包的业务代码共用的**。

所有包通过 `.asmref` 把同一层的代码汇入同一个程序集：

```
所有包的 Model 层代码      → 编译进 ET.Model
所有包的 Hotfix 层代码     → 编译进 ET.Hotfix
所有包的 ModelView 层代码  → 编译进 ET.ModelView
所有包的 HotfixView 层代码 → 编译进 ET.HotfixView
```

如果每个包各定义一套 asmdef，会有 `ET.LockStep.Model`、`ET.UI.Model`……程序集爆炸，互相引用也复杂。ET 的做法是**横切**：所有包的同一层代码进同一个程序集，Model 层内部可以直接互相访问类型。

其他基础工具包（npkparser、truesync、lsentity）不涉及 Entity/Component/System 模式，不分层也无所谓，一个 asmdef 就够了。

## 7. asmdef 名称必须全局唯一

两个 asmdef 的 `name` 不能重复，否则 Unity 编译报错：

> Assembly with name 'ET.MyLib' is already defined by 'Packages/xxx/Runtime/MyLib.asmdef'

所以命名规范是 `ET.包名.层级`，确保不冲突。

## 8. IDE 项目文件问题排查

如果 Rider/VS 中出现"无法解析符号"但 Unity 编译正常，通常是 IDE 项目文件过期：

- Unity 编译用的 asmdef（正确），但生成的 csproj 缺失或过期
- 检查方法：看项目根目录下是否缺少对应的 `.csproj` 文件
- 解决：Unity Editor → Edit > Preferences > External Tools → Regenerate project files
- Rider 缓存问题：File > Invalidate Caches > Invalidate and Restart
