# 技能系统架构方案

## 目标

基于 ET 框架帧同步实现类似 DNF/Dota 2 的技能系统，使用 C# 代码替代 Lua/Squirrel 编写技能逻辑生命周期，同时保持和 DNF/Dota 2 同等的技能表达能力。

---

## 一、传统技能系统架构参考

### 1.1 DNF（地下城与勇士）

```
┌──────────────────────────────────────────┐
│  C++ 引擎层                              │
│  - 渲染、物理、碰撞检测                    │
│  - 技能系统核心框架（SkillManager）         │
│  - Projectile / Hitbox / FrameData       │
├──────────────────────────────────────────┤
│  Squirrel 脚本层（每个技能一个 .nut 文件）   │
│  - SKILL_Init()                          │
│  - SKILL_Update(frameIndex)              │
│  - SKILL_OnHit(target)                   │
│  - SKILL_OnEnd()                         │
│  - 定义弹道轨迹、攻击判定框、帧事件          │
├──────────────────────────────────────────┤
│  数据配置层（NPK/SPR 动画 + Excel 表）     │
│  - 攻击力、冷却、范围等数值                 │
│  - 动画帧数据、特效绑定点                   │
└──────────────────────────────────────────┘
```

**要点**：技能逻辑就是 Squirrel 脚本，不是配置。一个技能的弹道生成、多段判定、状态切换、条件分支全是代码。C++ 层只提供 API（创建弹道、判定碰撞、播放动画、施加 buff）。根据台服泄露源码，写一个技能基本不涉及 C++ 代码。

### 1.2 Dota 2

```
┌──────────────────────────────────────────┐
│  C++ 引擎层（Source 2）                    │
│  - CAbilitySystem 核心框架                 │
│  - 内置 Ability 类型：线型/范围/指向/被动   │
│  - Modifier（buff/debuff）系统             │
│  - Projectile 系统                         │
├──────────────────────────────────────────┤
│  KV 配置 + Lua 脚本                        │
│  - KV: 声明技能属性（伤害、冷却、范围）     │
│  - Lua: 自定义逻辑（override 函数）         │
│    · OnSpellStart()                        │
│    · OnProjectileHit(target)               │
│    · OnOwnerDied()                         │
│    · GetCustomCastRange()                  │
├──────────────────────────────────────────┤
│  Modifier 同样是 KV + Lua                  │
│  - OnCreated / OnDestroy / OnInterval     │
│  - 声明式状态修改（属性加成/减益）           │
└──────────────────────────────────────────┘
```

**要点**：声明式 + 命令式混合。简单技能纯 KV 配置就能做，复杂技能写 Lua override。Modifier（buff/debuff）是一等公民，和 Ability 平级。

### 1.3 共性总结

| 层 | DNF | Dota 2 | 我们（C#） |
|---|---|---|---|
| 引擎/框架层 | C++ SkillManager | C++ CAbilitySystem | C# 技能系统包（ET Package） |
| 脚本/逻辑层 | Squirrel .nut | Lua | C# DLL（SkillDefs） |
| 数据配置层 | Excel + NPK | KV 文件 | Excel 配置表 |
| API 调用 | C++ 暴露给 Squirrel | C++ 暴露给 Lua | 框架 Model 层接口 |

## 二、我们的方案

### 2.1 架构总览

```
┌──────────────────────────────────────┐
│  技能系统核心包 cn.etetet.skill       │
│  - ISkillLogic 生命周期接口           │
│  - SkillEntity / SkillComponent      │
│  - Projectile / Hitbox / Buff 框架    │
│  - SkillLoader 运行时加载器           │
├──────────────────────────────────────┤
│  技能定义项目 ET.SkillDefs.dll       │
│  - 每个技能一个类，实现生命周期接口    │
│  - C# 代码，独立编译为 DLL            │
│  - 运行时由 SkillLoader 加载          │
├──────────────────────────────────────┤
│  数据配置层（Excel 配置表）            │
│  - 伤害数值、冷却、范围、buff ID       │
│  - 特效路径、音效路径                  │
└──────────────────────────────────────┘
```

**核心思路**：把 DNF 的 Squirrel / Dota 2 的 Lua 换成 C#。技能逻辑用代码而非纯配置表达。

### 2.2 为什么不能只用配置

**配置能搞定的（简单技能）**：
- 火球术：朝目标方向发射弹道，命中造成伤害
- 普攻：播放动画，帧 N 生成判定框

**必须代码表达的（复杂技能）**：
- DNF "血之狂暴"：多段连击 + 条件分支（命中/未命中走不同分支） + 自身 buff 叠加
- Dota 2 "拉比克"：复制对手上一个技能——纯配置无法表达
- DNF 觉醒技：多阶段演出 + 无敌帧 + 时间减速 + 屏幕震动 + 多次判定

DNF 用 Squirrel 写的恰恰是生命周期逻辑，这部分用配置表表达不了。

## 三、核心接口设计

### 3.1 技能生命周期接口

对标 DNF 的 Squirrel 回调（SKILL_Init/Update/OnHit 等）和 Dota 2 的 Lua override（OnSpellStart/OnProjectileHit 等）：

```csharp
public interface ISkillLogic
{
    // 生命周期
    void OnInit(SkillContext ctx);           // 技能创建
    void OnCast(SkillContext ctx);           // 开始释放
    void OnUpdate(SkillContext ctx, FP dt);  // 每帧更新（帧同步）
    void OnEnd(SkillContext ctx);            // 正常结束
    void OnInterrupt(SkillContext ctx);      // 被打断

    // 事件回调
    void OnHit(SkillContext ctx, HitResult hit);
    void OnProjectileHit(SkillContext ctx, Projectile proj, LSEntity target);
    void OnBuffApply(SkillContext ctx, Buff buff);

    // 帧同步确定性
    void GetHitboxData(int frame, out TSVector offset, out TSVector size);
}
```

### 3.2 基类设计（推荐）

用抽象基类提供默认实现，简单技能只填数据，复杂技能 override 逻辑：

```csharp
public abstract class SkillLogic : ISkillLogic
{
    // 数据部分——简单技能只需要填这些
    public virtual int TotalFrames => 60;
    public virtual FP Cooldown => FP.FromRaw(3000);
    public virtual FP ManaCost => FP.FromRaw(50);

    // 逻辑部分——复杂技能 override 这些
    public virtual void OnInit(SkillContext ctx) { }
    public virtual void OnCast(SkillContext ctx) { }
    public virtual void OnUpdate(SkillContext ctx, FP dt) { }
    public virtual void OnEnd(SkillContext ctx) { }
    public virtual void OnInterrupt(SkillContext ctx) { }
    public virtual void OnHit(SkillContext ctx, HitResult hit) { }
    public virtual void OnProjectileHit(SkillContext ctx, Projectile proj, LSEntity target) { }
    public virtual void OnBuffApply(SkillContext ctx, Buff buff) { }
    public virtual void GetHitboxData(int frame, out TSVector offset, out TSVector size)
    {
        offset = TSVector.zero;
        size = TSVector.zero;
    }
}
```

### 3.3 技能定义示例

```csharp
[SkillId(1001)]
public class Fireball : SkillLogic
{
    public override void OnCast(SkillContext ctx)
    {
        ctx.CreateProjectile(
            templateId: 2001,
            origin: ctx.Caster.Position,
            direction: ctx.TargetDirection,
            speed: FP.FromRaw(15)
        );
    }

    public override void OnProjectileHit(SkillContext ctx, Projectile proj, LSEntity target)
    {
        ctx.DealDamage(target, FP.FromRaw(100));
    }
}
```

### 3.4 技能加载器

```csharp
public static class SkillLoader
{
    private static readonly Dictionary<int, Func<ISkillLogic>> factories = new();

    public static void Load(Assembly skillAssembly)
    {
        foreach (var type in skillAssembly.GetTypes())
        {
            if (typeof(ISkillLogic).IsAssignableFrom(type) && !type.IsAbstract)
            {
                var attr = type.GetCustomAttribute<SkillIdAttribute>();
                if (attr != null)
                {
                    var id = attr.Id;
                    factories[id] = () => (ISkillLogic)Activator.CreateInstance(type);
                }
            }
        }
    }

    public static ISkillLogic Create(int skillId)
    {
        return factories.TryGetValue(skillId, out var factory) ? factory() : null;
    }
}
```

## 四、帧同步约束

技能逻辑在 LSWorld 中运行，必须遵守帧同步确定性规则：

### 4.1 必须遵守

- 只使用 `FP` / `TSVector` / `TSVector2` / `TSQuaternion`（TrueSync 定点数）
- 随机数用 `TSRandom`，不用 `System.Random` 或 `UnityEngine.Random`
- 不使用 `float` / `double`
- 不使用 `DateTime` / `Environment.TickCount`
- 不访问非确定性状态（如 `transform.position`）
- LSEntity 必须用 `[MemoryPackable]` 标记

### 4.2 C# vs 脚本在确定性上的优势

| 维度 | C# DLL | Squirrel/Lua |
|------|--------|--------------|
| 类型安全 | 强类型，编译期检查 | 弱类型，运行时才发现 |
| 浮点误用 | FP 类型显式声明，不易混用 float | 数字类型无区分，容易误用浮点 |
| 单元测试 | 可写测试验证确定性 | 较难做自动化验证 |
| 调试 | 完整断点/变量监视 | 有限的调试支持 |

## 六、调试流程

### 6.1 开发期（90% 时间）—— 直接在 Hotfix 层

技能代码放在 ET 包的 Hotfix 目录内，走 Unity 正常编译：

```
改 Berserk.cs → Ctrl+S → Unity 自动重编译 → 进游戏测试
```

- Rider/VS 断点、单步、变量监视全部可用
- HybridCLR 热更代码也支持调试（Unity Editor Attach）
- 和写普通 C# 没有区别，不需要走"编译 DLL → 加载 → 测试"循环

### 6.2 断点调试帧同步逻辑

```csharp
public override void OnUpdate(SkillContext ctx, FP dt)
{
    // 断点在此，检查所有定点数计算是否正确
    var pos = ctx.Caster.Position;        // TSVector
    var offset = TSVector.forward * dt;   // FP 运算

    // 关键确认：同一帧、同一输入，两次执行结果必须完全一致
}
```

### 6.3 调试帧同步确定性

```
发现不同步（哈希校验失败）
  → 用 Replay 系统回放
  → 在关键帧打断点对比两次执行
  → 逐帧对比 FP/TSVector 的值
  → 定位到哪个技能的哪次计算出了偏差
```

常见非确定性 bug 来源：
- 使用了 `System.Random` 而非 `TSRandom`
- 使用了 `float` 而非 `FP`
- 使用了 `DateTime.Now` 等非确定性 API
- LSEntity 字段未标记 `[MemoryPackable]` 导致快照不完整

### 6.4 DLL 加载阶段调试

技能稳定后移到独立项目编译 DLL，需要验证：

```csharp
// 加载器日志确认注册成功
public static void Load(Assembly assembly)
{
    foreach (var type in assembly.GetTypes())
    {
        Log.Info($"注册技能: id={attr?.Id}, type={type.Name}");
    }
}
```

常见 DLL 加载问题：
- DLL 没放到正确位置 → 加载不到
- 接口版本不匹配（框架改了接口，DLL 没重编）→ `MissingMethodException`
- 编译条件不一致（忘了 `DOTNET` 宏）→ 条件编译导致代码缺失

## 七、方案对比总结

### 7.1 vs DNF（Squirrel）

| 维度 | DNF | 我们 |
|------|-----|------|
| 脚本语言 | Squirrel | C# |
| 开发体验 | 弱类型，IDE 补全差 | 强类型，完整 IDE 支持 |
| 性能 | 解释执行 | 编译执行，接近原生 |
| 热更新 | 天然支持 | HybridCLR 支持 |
| 帧同步确定性 | 弱类型容易出 bug | 强类型更易保证 |
| 表达能力 | 同等（都是写生命周期代码） | 同等 |

### 7.2 vs Dota 2（Lua）

| 维度 | Dota 2 | 我们 |
|------|--------|------|
| 脚本语言 | Lua | C# |
| 配置格式 | KV 文件 | Excel 配置表 |
| Buff 系统 | Modifier（一等公民） | Buff/Modifier（同设计） |
| 声明式支持 | KV 属性声明 | Excel + 基类默认值 |
| 调试 | 有限 | 完整断点/Profiler |

### 7.3 独立项目 vs ET 包

| 维度 | ET 包 | 独立 C# 项目（推荐） |
|------|-------|---------------------|
| 与核心包耦合 | 高 | 低，只通过接口通信 |
| 热更新 | 依赖整体 HybridCLR | 天然支持，DLL 本身就是热更产物 |
| 技能间隔离 | 无，同一程序集 | 可按角色分包 |
| 新增技能 | 改包代码 → 重编热更 DLL | 加一个 .cs → 编译 → 替换 DLL |
| 内容属性 | 偏"系统" | 偏"内容"，和 DNF 脚本定位一致 |

## 九、待确认问题

以下问题在实际实现时需要进一步确认：

1. **技能 DLL 是否需要按角色分包**：如果所有技能打包成一个 DLL，改一个技能要全量重编。角色多时可考虑按角色拆分
2. **技能间触发规则**：`SkillContext.CastSkill(id)` 是技能间触发的外部 API（内部通过事件系统或组件查找分发），需要明确的是触发规则——技能 A 能触发哪些技能？是否受冷却/MP/状态限制？是否允许递归触发（A→B→A）？需要防止技能间形成循环依赖
3. **Buff/Modifier 系统**：是否需要和 Dota 2 一样作为一等公民独立于技能？还是作为技能的子组件？
4. **连招系统**：DNF 的连招（技能取消技能）需要额外的状态机或 combo 树设计
5. **技能与动画同步**：帧同步中技能逻辑帧和动画帧如何对齐？需要明确的帧事件机制
6. **编译 DLL 的触发时机**：手动编译还是 CI 自动编译？如何与版本管理配合？
